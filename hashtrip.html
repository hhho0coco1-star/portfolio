HashTrip

여행 성향 분석부터 일정 공유까지, 내 취향에 맞는 여행을 계획하는 플랫폼

📅 기간: 2026.02.09 ~ 2026.03.04 👥 팀 구성: 5명 🔗 GitHub 링크 🎬 시연 영상
Java 11 Spring Framework Spring Security MyBatis OAuth2 Spring Mail JSP Vanilla JS Oracle Maven

기술 선택 이유

  • JSP 서버 렌더링 — 페이지 단위 이동 중심 서비스라 SPA 없이 서버 렌더링으로 개발 속도 우선.
  • OAuth2 3종(Google·Kakao·Naver) — 여행 서비스 특성상 가입 장벽을 낮추기 위해 소셜 로그인 통합.
  • MyBatis — 성향 분석 태그 집계·여행지 매칭 등 복잡한 조인 쿼리를 SQL로 직접 제어.
  • ExecutorService 병렬 처리 — 순차 처리로 누적되던 운영시간 파싱을 6~12 스레드 병렬 구조로 전환.
🧭 여행 성향 분석 설문 기반 태그 가중치 합산으로 개인 맞춤 여행 스타일 도출
📅 여행 일정 계획 공공API 여행지 기반 일정 생성·공유 및 루트 북마크
🗺️ 여행지 탐색 한국관광공사 API 기반 장소 검색·평점·운영시간 제공
🔑 소셜 로그인 Google · Kakao · Naver OAuth2 통합 인증 지원

담당 범위 및 역할

핵심 알고리즘 담당 최종 발표 Backend 중심 풀스택

왜 이 역할을 맡았나

HashTrip의 차별점은 성향 기반 맞춤 추천이고, 그 심장인 성향 분석 알고리즘을 직접 설계하고 싶어 맡았습니다. 추천 품질은 입력 데이터에 좌우되기 때문에, 데이터를 공급하는 공공 데이터 수집 파이프라인까지 함께 담당해 '수집 → 분석 → 추천'을 한 흐름으로 책임졌습니다. 프로젝트 전반을 꿰고 있어 최종 발표도 맡았습니다.

핵심 도메인 설계

성향 분석 · 여행 일정 흐름 중심 핵심 테이블 발췌

  1. 태그는 여러 장소에 재사용되고 자동 분류의 가중치·신뢰도를 함께 남겨야 해, N:M 중간 테이블(Place_Tag_Map)에 tag_weight · tag_confidence 컬럼을 두어 분리했습니다.
  2. 사용자 성향(User_Tag_Map)을 설문 질문별로 분리 저장해 질문 단위 가중치 합산 분석을 지원했습니다.
  3. Travel_Plans와 Plan_Details를 분리해 계획 단위와 장소별 방문 순서(plan_visit_order)를 독립 관리했습니다.

트러블슈팅 및 개선 포인트

성향 분석 결과 중복 태그 시 오산출 → 오류 케이스 0건 ✅
⚠️
문제 상황

1:1 선택지 설문에서 사용자가 모든 질문에 답변한 후 성향 분석 결과를 도출할 때, 동일 태그가 여러 질문에 걸쳐 중복 등장하는 경우 결과가 부정확하게 산출되는 오류가 발생했습니다. 일부 케이스에서 실제 가장 많이 선택한 태그가 아닌 다른 태그가 최종 성향으로 결정되었습니다.

🔍
원인 분석

초기 로직은 선택한 태그의 존재 여부만 비교하는 SQL 문자열 매칭 방식이었습니다. 같은 태그가 여러 질문에서 반복 선택돼도 빈도가 반영되지 않아, 실제 선택 빈도가 낮은 태그가 매칭 결과상 먼저 등장해 잘못된 성향으로 결정되는 경우가 발생했습니다.

🛠️
해결 과정

'태그 유무 비교' 방식을 폐기하고, '질문별 가중치 합산' 방식으로 로직을 전면 수정했습니다. 각 질문에서 선택한 태그에 질문별 가중치를 부여하고, 동일 태그가 여러 질문에서 선택될수록 합산 점수가 누적되도록 Oracle SQL 가중치 합산 쿼리(SUM·GROUP BY)로 변경했습니다. 전체 질문 답변 완료 후 가장 높은 합산 점수를 가진 태그를 최종 여행 스타일로 결정합니다.

✅
결과

중복 태그가 발생하는 모든 케이스에서 사용자가 실제로 가장 많이 선택한 태그가 정확하게 최종 여행 스타일로 결정됩니다. 로직 수정 후 성향 분석 결과 오류 케이스 0건을 확인했습니다.

상세 정보 수집 단건 순차(Blocking) → 6~12 스레드 병렬 ⚡
⚠️
문제 상황

관리자가 한국관광공사 공공 API로 여행지 데이터를 수집할 때, 여행지별 상세 정보(운영시간 등)를 하나씩 순차 조회하다 보니 전체 수집 시간이 과도하게 길어졌습니다. 수집 대상 여행지가 많아질수록 소요 시간이 비례해 누적되었습니다.

🔍
원인 분석

여행지 데이터를 순차적(Sequential)으로 하나씩 API 호출·DB 조회하는 구조였습니다. 데이터 양에 비례하여 전체 수집 시간이 누적되는 구조적 문제였으며, 앞선 처리가 완료될 때까지 다음 처리가 시작되지 못하는 Blocking이 발생했습니다.

🛠️
해결 과정

단건 순차 조회 방식을 ExecutorService 기반 병렬 처리(6~12 스레드)로 변경했습니다. 수집된 여행지의 운영시간 등 상세 정보 조회를 여러 스레드로 동시에 수행하고, 수집 결과는 300건 단위 배치 INSERT로 저장해 DB 부하까지 함께 줄였습니다.

✅
결과

기존 순차 처리 대비 상세 정보 수집 시간을 체감상 크게 단축했습니다(정밀 벤치마크 로그는 별도로 남기지 못함). 배운 점: 외부 API 대량 호출은 병렬화와 배치 저장만으로도 처리 시간을 크게 줄일 수 있다.

회고 및 배운 점

⚙️

기술적 성장

한국관광공사 공공API 대량 데이터를 ExecutorService 병렬 처리와 배치 INSERT로 효율적으로 수집하는 방법을 익혔습니다. 성향 분석 알고리즘을 직접 설계하고, 태그 중복 처리 버그를 발견·수정하는 과정에서 알고리즘의 엣지 케이스를 꼼꼼히 검토하는 습관이 생겼습니다. Spring Security OAuth2 소셜 로그인 3종 연동을 통해 인증 흐름 전반을 이해하게 되었습니다.

🤝

협업 경험

최종 발표를 담당하면서 프로젝트 전반을 명확하게 정리하고 전달하는 능력을 키웠습니다. 팀원들의 구현 내용을 통합적으로 이해하고 아키텍처 전체 흐름을 파악하는 시야가 생겼습니다. 발표 준비 과정에서 팀 전원의 코드를 리뷰하며 각 모듈의 연결 지점을 직접 확인했습니다.

🎯

다음 목표

HashTrip이 '추천'에 집중했다면, 다음에는 사용자가 직접 현장을 방문하고 참여하도록 만드는 서비스에 도전하고 싶습니다. 퀘스트·포인트·배지 같은 게임화 요소로 참여 동기를 높이고, React SPA 기반의 풍부한 인터랙션과 위치·QR 현장 인증, 나아가 매장(비즈니스 파트너)까지 연결되는 O2O 생태계로 확장하는 것이 다음 목표입니다.
