담당 범위 및 역할

핵심 알고리즘 담당 최종 발표 Backend 중심 풀스택

왜 이 역할을 맡았나

HashTrip의 차별점은 성향 기반 맞춤 추천이고, 그 심장인 성향 분석 알고리즘을 직접 설계하고 싶어 맡았습니다. 설문 응답을 어떻게 점수화해 하나의 여행 스타일로 수렴시킬지를 데이터 구조부터 설계했고, 메인·관리자 페이지를 풀스택으로 함께 담당했습니다. 프로젝트 전반을 꿰고 있어 최종 발표도 맡았습니다.

핵심 도메인 설계

성향 분석 · 여행 일정 흐름 중심 핵심 테이블 발췌

  1. 태그는 여러 장소에 재사용되고 자동 분류의 가중치·신뢰도를 함께 남겨야 해, N:M 중간 테이블(Place_Tag_Map)에 tag_weight · tag_confidence 컬럼을 두어 분리했습니다.
  2. 사용자 성향(User_Tag_Map)을 설문 질문별로 분리 저장해 질문 단위 가중치 합산 분석을 지원했습니다.
  3. Travel_Plans와 Plan_Details를 분리해 계획 단위와 장소별 방문 순서(plan_visit_order)를 독립 관리했습니다.

성향 분석 아키텍처 및 흐름

설문 진입부터 성향 판정 · 추천 · 일정 등록까지의 전체 경로

Phase 1. 로그인 & 설문 진입
API
설문 진입로그인 확인 후 GET /analysis — 질문·선택지 목록 로드 → JSP 설문 화면 렌더링
Phase 2. 설문 응답 수집
Frontend
응답 제출질문별 A/B 선택으로 태그 코드 누적 → POST /analysis/result로 선택 태그 목록 전송
Phase 3. 성향 분석 & 결과 저장
Service
가중치 합산 분석AnalysisController → UserTagMapServiceImpl — 선택 태그를 Oracle SQL 집계(SUM·GROUP BY)로 누적 합산해 최다 점수 태그를 여행 스타일로 결정. 결과 판정을 애플리케이션이 아닌 쿼리에서 끝내 로직을 한 곳에 모았습니다.
↓
DB
결과 저장 & 표시UserTagMapDAO · TravelStylesDAO — User_Tag_Map·Travel_Styles INSERT → 여행 스타일·추천 태그 결과 페이지 렌더링
Phase 4. 성향 기반 추천 여행지 조회
DB
성향 코드 기반 여행지 매칭GET /places/recommend → Travel_Styles 성향 코드로 Place_Tag_Map JOIN Place JOIN Tag_Master 조회 · 가중치·평점 정렬
↓
Frontend
추천 여행지 목록 렌더링여행지명 · 주소 · 평점 · 매칭 태그 카드 표시
Phase 5. 여행 일정에 여행지 등록
API
여행지 등록 요청추천 카드에서 "일정에 추가" → 기존/신규 일정 선택 → POST /plan (TravelPlanService.insertTravelPlanWithDetails)
↓
DB
일정 & 상세 저장Travel_Plans·Plan_Details INSERT (방문 순서·날짜·메모) — @Transactional → 내 여행 일정 페이지 이동

트러블슈팅 및 개선 포인트

성향 분석 결과 중복 태그 시 오산출 → 오류 케이스 0건 ✅
⚠️
문제 상황

1:1 선택지 설문 10문항에 답변을 마치면 최종 여행 스타일을 산출하는데, 초기 버전은 TRAVEL_ANALYSIS_MASTER 테이블에서 문항별(Q1_PLACE·Q2_PLAN·Q9_ENERGY) 선택 조합키를 그대로 조회해 매칭하는 방식이었습니다. 동일 태그가 여러 질문에 걸쳐 중복 선택되면 실제 가장 많이 고른 태그가 아닌 다른 태그가 최종 성향으로 결정되는 오류가 나왔습니다.

🔍
원인 분석

기존 getFinalAnalysisResult 조회는 선택한 조합키가 마스터 테이블에 존재하는지만 보는 문자열 매칭이라, 같은 태그를 여러 문항에서 반복 선택해도 그 빈도가 결과에 반영되지 않았습니다. 선택 횟수를 세는 로직 자체가 없어서, 1번 선택된 태그가 매칭 순서상 먼저 걸리면 3번 선택된 태그를 제치고 그대로 최종 결과가 되는 구조였습니다.

🛠️
해결 과정

UserTagMapServiceImpl.processUserAnalysis()를 전면 수정했습니다. TRAVEL_ANALYSIS_MASTER를 걷어내고 TAG_WEIGHT_MASTER·TRAVEL_RESULT_MAPPING 테이블을 새로 설계해, users_mapper.xml의 getTravelAnalysisData 쿼리에서 태그 코드를 카테고리(PLACE/ENERGY/PLAN)로 매핑한 뒤 SUM(W.WEIGHT) ... GROUP BY W.CATEGORY로 문항별 선택 빈도를 합산하도록 바꿨습니다. 질문 3개(QUESTION_ID 1, 2, 9) 각각에서 합산 점수가 가장 높은 카테고리를 뽑아 최종 문구를 구성합니다.

✅
결과

중복 태그가 있는 모든 케이스에서 실제 선택 빈도가 가장 높은 태그가 최종 여행 스타일로 결정되도록 수정 후 오류 케이스 0건을 확인했습니다. 문자열 비교 → 가중치 계산으로 방식을 바꾼 덕분에, 이후 성향 문항이 늘어나도 카테고리·가중치 테이블만 추가하면 로직 변경 없이 확장할 수 있습니다.

여행지 상세 수집 순차 조회 → 6~12 스레드 병렬 ✅
⚠️
문제 상황

한국관광공사 공공 API에서 여행지 상세 정보를 수집할 때 단건 API 호출을 순차적으로 반복하다 보니, 데이터 수가 늘어날수록 응답 시간이 그만큼 누적돼 로딩 속도가 현저히 저하됐습니다.

🔍
원인 분석

API 호출 1건씩 응답을 기다린 뒤 다음 요청을 보내는 구조라, 전체 소요 시간이 건당 응답 시간과 데이터 건수에 비례해 선형으로 증가했습니다.

🛠️
해결 과정

ExecutorService 기반 스레드풀(6~12개)로 API 호출을 병렬 처리하고, 수집한 결과는 300건 단위로 배치 INSERT해 DB 왕복 횟수도 함께 줄였습니다.

✅
결과

건수에 비례해 선형으로 늘던 수집 시간을 스레드 수만큼 분할했고, 건당 INSERT를 300건 배치로 묶어 DB 왕복 횟수도 줄였습니다.

회고 및 배운 점

⚙️

기술적 성장

성향 분석 알고리즘을 직접 설계하고, 태그 중복 처리 버그를 발견·수정하는 과정에서 알고리즘의 엣지 케이스를 꼼꼼히 검토하는 습관이 생겼습니다. 문자열 매칭으로는 선택 빈도를 반영할 수 없다는 한계를 확인하고 SQL 집계(SUM·GROUP BY) 기반으로 전환하며, 요구사항을 데이터 구조로 옮기는 판단을 경험했습니다. Spring Security OAuth2 소셜 로그인 3종 연동을 통해 인증 흐름 전반을 이해하게 되었습니다.

🤝

협업 경험

최종 발표를 담당하면서 프로젝트 전반을 명확하게 정리하고 전달하는 능력을 키웠습니다. 팀원들의 구현 내용을 통합적으로 이해하고 아키텍처 전체 흐름을 파악하는 시야가 생겼습니다. 발표 준비 과정에서 팀 전원의 코드를 리뷰하며 각 모듈의 연결 지점을 직접 확인했습니다.
