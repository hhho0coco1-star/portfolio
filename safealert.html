SafeAlert

재난·기상·미세먼지 공공 API를 구독하고 WebSocket으로 실시간 알림을 받는 MSA 기반 구독 서비스

📅 기간: 2026.05.13 ~ 2026.06.08 👤 개인 프로젝트 🔗 GitHub 링크
Java 17 Spring Boot 3.3 Spring Cloud Gateway Apache Kafka WebSocket (STOMP) JWT OAuth2 Resilience4j PostgreSQL MongoDB Redis React Docker Kubernetes Prometheus Grafana Jaeger ELK Stack k6

기술 선택 이유

  • MSA + Kafka — 수집·처리·알림 역할을 분리하면 각 서비스를 독립 확장·배포할 수 있고, Kafka를 중간에 두면 수집 속도와 처리 속도를 분리해 부하를 흡수합니다.
  • Transactional Outbox 패턴 — DB 저장과 Kafka 발행을 하나의 트랜잭션으로 묶어 알림 유실을 방지합니다. Kafka에 직접 발행하면 DB 실패 시 메시지가 이미 나간 상태가 될 수 있어 이 패턴을 택했습니다.
  • Redis Pub/Sub — 알림 서비스가 K8s에서 replica 3으로 뜰 때, 어느 인스턴스가 알림을 처리하든 Redis 채널로 발행하면 모든 인스턴스가 각자 연결된 사용자에게 WebSocket Push를 전달할 수 있습니다.
  • Circuit Breaker (Resilience4j) — 공공 API 응답 지연·장애 시 연쇄 장애를 막기 위해 도입했습니다. API가 불안정해도 나머지 서비스는 계속 동작합니다.
  • PostgreSQL + MongoDB 혼용 — 사용자·구독 정보처럼 관계가 명확한 데이터는 PostgreSQL, 알림 내용처럼 스키마가 API마다 다른 데이터는 MongoDB에 저장해 각 DB의 강점을 활용했습니다.
  • Kubernetes — replica 설정으로 수평 확장, Rolling Update로 무중단 배포, ConfigMap/Secret으로 환경 분리를 목적으로 선택했습니다.

팀 프로젝트에서 쌓은 Spring·React 경험을 바탕으로, MSA·Kafka·K8s 같은 실무 기술을 직접 설계·구현하며 체득하기 위해 개인 포트폴리오 프로젝트로 기획했습니다. 단순 기능 구현에서 나아가 부하 테스트(k6)·분산 트레이싱(Jaeger)·로그 집계(ELK)·메트릭 모니터링(Prometheus·Grafana)까지 운영 환경에 가까운 스택을 경험하는 것이 목표였습니다.

왜 이 프로젝트를 기획했나

팀 프로젝트에서는 Spring MVC·Oracle 중심의 모놀리식 구조만 경험했습니다. 실무에서 자주 언급되는 MSA·Kafka·K8s를 직접 설계해보지 않으면 구조를 진정으로 이해하기 어렵다고 판단해 처음부터 끝까지 혼자 기획·구현·운영까지 수행했습니다. 단순 CRUD가 아닌 분산 환경의 문제(데이터 유실, 다중 인스턴스 WebSocket, 연쇄 장애)를 직접 맞닥뜨리고 해결하는 경험이 목적이었습니다.

트러블슈팅 및 개선 포인트

문제 상황

Notification Service를 K8s replica 3으로 배포 후, 브라우저에서 WebSocket으로 연결해도 알림이 오지 않는 경우가 간헐적으로 발생. 재현 조건: 알림을 처리한 서버 인스턴스와 사용자가 연결된 인스턴스가 다를 때.

↓
원인 분석

WebSocket 세션은 서버 메모리에 저장된다. 인스턴스 A에 연결된 사용자 세션을 인스턴스 B는 알 수 없어 Push 불가. 서버 1대일 때는 발생하지 않아 replica 증가 후에야 발견했다.

↓
해결 과정

Redis Pub/Sub 도입 — 어느 인스턴스가 알림을 처리하든 alert:public 채널에 발행. 모든 인스턴스가 채널을 구독하다가 자신에게 연결된 사용자에게 Push. AlertPublicSubscriber.java 신규 생성, RedisConfig.java에 ChannelTopic 등록.

↓
결과

replica 3개 환경에서 전국 알림 1건 발생 시 3개 인스턴스 모두 WebSocket 전달 확인. 배운 점: 분산 환경에서 상태(세션)를 서버 메모리에 저장하면 안 된다 → Stateless 설계 원칙.

문제 상황

docker-compose에 Jaeger all-in-one 추가 후 6개 서비스에 OpenTelemetry javaagent 설정. Jaeger UI(localhost:16686)에서 서비스 목록이 비어 있음 — 트레이스 수집이 전혀 안 됨.

↓
원인 분석

gRPC(4317)로 설정했으나 두 가지가 겹쳤다: ① docker-compose 로컬 환경에서 HTTP/2(gRPC)가 안정적이지 않음 ② OpenTelemetry javaagent 기본값이 gRPC인데 Jaeger의 gRPC 수신이 명시적으로 활성화되지 않음.

↓
해결 과정

otel.exporter.otlp.endpoint 포트를 4317 → 4318(HTTP/protobuf)로 전환. HTTP/1.1 기반이라 로컬 환경 제약을 받지 않음.

↓
결과

Jaeger UI에서 6개 서비스 트레이스 수집 확인. 배운 점: "설정했는데 안 된다" 상황에서 디버깅 순서 — 로그 확인 → 포트 확인 → 공식 문서 기본값 확인 → 더 단순한 방법부터 시도.

문제 상황

5월 31일에 한파·대설 같은 겨울 알림이 수집되는 현상 발견. 분명히 과거 데이터인데 신규 알림처럼 처리됨.

↓
원인 분석

Redis 중복 필터의 TTL이 24시간. 행정안전부 API는 과거 데이터도 함께 반환하는데, TTL 만료 후에는 중복 키가 사라져 과거 알림이 신규처럼 재수집됨.

↓
해결 과정

API 응답의 crtDt 필드를 파싱해 오늘 날짜와 비교하는 필터 추가. 오늘 날짜가 아닌 데이터는 루프에서 continue로 건너뜀. 기상청(현재 활성 알림만 반환)·미세먼지(중복 키에 날짜 포함)는 이 문제가 없어 행정안전부만 적용.

↓
결과

과거 알림 재수집 0건 확인. 배운 점: 외부 API를 사용할 때는 응답 데이터의 날짜·범위 조건을 직접 확인해야 한다.

문제 상황

k6 로그인 부하 테스트 (100 VU, 3분) 실행 결과 오류율 97.85%. p95 기준 2.66s로 목표(2s) 초과.

↓
원인 분석

HikariCP 기본 maximum-pool-size가 10. 100명이 동시에 로그인하면 90명이 커넥션을 기다리다 타임아웃. Rate Limiting도 동일 IP 100개 요청을 차단하고 있었음.

↓
해결 과정

① Rate Limiting 로컬호스트(127.0.0.1) 화이트리스트 추가 ② auth-service HikariCP maximum-pool-size 10 → 30으로 조정 후 재테스트.

↓
결과

오류율 0% · p95 2.66s → 1.86s (30% 개선) · 목표 2s 이하 달성. 배운 점: DB 커넥션 풀은 동시 요청 수를 고려해 설정해야 한다. 기본값이 실무와 다를 수 있다.

MSA 구조에서 발생하는 문제들(알림 유실, 다중 인스턴스 WebSocket, 연쇄 장애)을 직접 설계하고 해결하면서 왜 Outbox 패턴·Redis Pub/Sub·Circuit Breaker가 필요한지 체감했습니다. 이론으로만 알던 개념들이 실제 장애를 통해 몸에 새겨졌습니다.

☸️

운영 환경 경험

Kubernetes에서 replica를 늘렸을 때 발생하는 문제, HikariCP 튜닝이 p95에 미치는 영향, Jaeger로 서비스 간 응답 시간을 추적하는 과정을 직접 수행했습니다. 개발과 운영이 얼마나 다른지 실감했고, 배포 이후를 고려한 설계 감각이 생겼습니다.
