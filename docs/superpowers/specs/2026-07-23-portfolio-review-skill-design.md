# 포트폴리오 리뷰 스킬 설계

## 배경
1p(hero) 슬라이드에서 "자격증 2"가 핵심역량과 나란히 노출되는 등, 채용담당자가 짧게 훑어볼 때
우선순위가 맞지 않는 구간이 있었다. 매번 대화로 즉흥적으로 기준을 설명하는 대신, 냉정한 평가 기준을
스킬로 고정해두고 이후 포트폴리오를 수정할 때마다 재사용한다.

## 범위
- 대상: `c:\study\portfolio` 사이트(index.html 및 상세 페이지)
- 이번 사이클은 포트폴리오 리뷰 스킬 하나만 다룬다. "개발 전반의 토큰 효율화" 같은 더 넓은 주제는
  별도 브레인스토밍 사이클로 분리한다 (범위 과다 방지).

## 트리거
- 사용자가 명시적으로 요청할 때(`/portfolio-review` 또는 "포트폴리오 평가해줘" 류의 발화)
- **그리고** 포트폴리오 코드를 수정하는 작업 중, Claude가 판단하기에 아래 평가 기준에 걸리는
  변경이 생겼을 때는 사용자가 요청하지 않아도 먼저 알린다 (이번 대화에서 사용자가 명시적으로
  요청한 동작 — "그때마다 알려줘")

## 절차
1. `python -m http.server`로 `portfolio/` 정적 서버를 임시로 기동
2. 헤드리스 크롬(CDP)으로 대상 페이지를 렌더링해 섹션/슬라이드별 스크린샷 확보
3. 같은 페이지의 HTML 텍스트(문구·배치 순서)를 함께 읽음
4. 아래 5개 평가 기준에 맞춰 채점
5. 서버·크롬 프로세스 정리
6. 우선순위별([HIGH]/[MED]/[LOW]) 개선안 리포트를 텍스트로 출력 — **코드는 수정하지 않음**
   (실제 반영은 사용자 승인 후 별도 작업으로 진행, 기존 `feedback_approval_before_action` 원칙과 동일)

## 평가 기준 (2026-07 리서치 반영)
리서치 근거: 국내 채용담당자는 이력서/포트폴리오를 평균 30초~1분 훑어보며 스펙 나열보다
"무엇을 만들었고 어떤 문제를 해결했는지"를 우선 확인한다. 해외 6초 스캔 리서치에서는 스크롤 없이
보이는 영역에 스킬/역량이 바로 보여야 하고, 정량 지표가 첫 화면에 있어야 통과율이 높다고 나타난다.

1. **첫 화면 스킵 테스트** — 스크롤 없이 보이는 영역에서 "핵심역량"이 "스펙/자격증"보다
   시각적으로 먼저·크게 보이는가
2. **숫자=역량 매칭** — 정량 지표(숫자)가 있다면 그 라벨이 역량을 설명하는가, 단순 스펙 나열인가
   (예: "자격증 2"는 ❌, "MSA 5개 단독설계"는 ✅)
3. **문제→과정→해결→결과 구조** — 프로젝트 설명에 이 흐름이 있는지, 결과가 정량화됐는지
4. **훑어보기 밀도** — 한 화면/섹션의 정보량이 6초~수십 초 안에 못 읽을 만큼 빽빽한 구간이 있는지
5. **정보 위계 순서** — 스펙(자격증·학력)이 상대적으로 뒤 슬라이드로 밀려 있고, 역량·프로젝트가
   앞에 오는 구조인지

## 출력 형식 예시
```
[HIGH] 1p 상단 "자격증 2" 통계 카드 — 핵심역량보다 시각적 우선순위가 높음
  → 근거: hero 영역 3개 통계 중 하나가 자격증 개수. 채용담당자는 첫 화면에서
    "이 사람이 뭘 잘하는가"를 먼저 찾는데, 자격증은 그 질문에 답하지 않음
  → 개선안: "자격증 2" 자리에 핵심역량 지표로 교체, 자격증은 5p(경험&자격증)로 이동

[MED] ...
```

## 하지 않는 것 (Non-goals)
- 코드 자동 수정(`--fix` 없음) — 평가·개선안 제시까지만
- 색감·서체 등 주관적 심미성 평가 — "스캔 가능성"과 "정보 우선순위"에 집중
- 매 실행마다 서브에이전트 기동 — 토큰/레이턴시 절약을 위해 현재 대화에서 직접 수행
- "개발 전반의 토큰 효율화" 같은 더 넓은 워크플로우 설계 — 별도 사이클

## 향후 확장 (이번 사이클 범위 아님, 메모만)
- 포트폴리오 리뷰 외에 개발 전반에 적용할 "원하는 결과 + 토큰 절약" 원칙은 사용자가 향후
  별도로 브레인스토밍하고 싶어함. 이 스킬의 구조(경량 단일 스킬, 고정 기준표, 스크린샷 기반 검증)가
  그 다음 논의의 참고 사례가 될 수 있음.
