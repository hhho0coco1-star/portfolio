기술 선택 이유

  • JWT + 세션 이원화 — 사용자·비즈니스 React SPA는 stateless JWT, 관리자 JSP는 서버 세션으로 분리(클라이언트 성격에 맞춰).
  • React + JSP 혼용 — 상호작용 많은 사용자·비즈니스 화면은 React SPA, 빠른 개발이 중요한 관리자 CRUD는 JSP 서버 렌더링.
  • MyBatis — 비즈니스 대시보드의 통계성 집계 쿼리를 SQL로 직접 제어·튜닝하기 위해 선택했습니다.
  • Kakao Map + QR — 위치 기반 현장 방문이 핵심이라 지도 표시와 현장 인증(QR)이 필수. 운영중지 매장·방문 순서·시간초과·중복완료 4가지로 부정 사용을 검증했습니다.

담당 범위 및 역할

👑 팀 리더 Backend 중심 풀스택

왜 이 역할을 맡았나

5인 팀의 리더로서, 서비스 신뢰성을 좌우하는 현장 인증(QR)과 운영의 중심인 관리자·비즈니스 영역을 직접 맡았습니다. QR 인증은 부정 사용을 막아야 하는 핵심 검증 로직이라 설계부터 끝까지 한 사람이 통제해야 한다고 판단했고, 프론트와 백엔드 어느 한쪽만 봐서는 흐름이 끊기기 때문에 풀스택으로 담당했습니다.

핵심 도메인 설계

퀘스트 수행 흐름 중심 핵심 테이블 발췌 (전체 29개 테이블 중 7개)

  1. 퀘스트에 장소를 직접 컬럼으로 넣을 수도 있었지만, 한 장소가 여러 퀘스트에 재사용되고 방문 순서가 필요해 N:M 중간 테이블(LQ_QUEST_LOCATION)로 분리하고 VISIT_ORDER를 두었습니다.
  2. 진행 단위를 LQ_USER_QUEST_PROGRESS로 세분화하여 장소별 완료 여부를 독립적으로 추적했습니다.
  3. 영수증 인증(LQ_RECEIPT)을 LQ_USER_QUEST_PROGRESS와 1:1로 연결해 인증 이력을 명확히 관리했습니다.

트러블슈팅 및 개선 포인트

반복 진입·이탈 후 메모리 점진적 증가(누수) → 일정 유지 ✅
⚠️
문제 상황

비즈니스 대시보드의 QR 탭(useBusinessOverview 훅)을 반복해서 진입·이탈하면 브라우저 메모리 사용량이 점진적으로 증가했습니다. QR 이미지가 API 응답마다 새 Blob으로 내려오는 구조라, 대시보드를 오래 켜두고 새로고침을 반복하는 매장 운영자 입장에서는 장시간 사용 시 탭이 눈에 띄게 느려지는 문제였습니다.

🔍
원인 분석

loadBusinessOverview()에서 QR 이미지 Blob을 받아 URL.createObjectURL(qrBlob)으로 변환해 <img> src에 그대로 바인딩했습니다. createObjectURL()이 만든 URL은 revokeObjectURL()을 명시적으로 호출하기 전까지 브라우저 메모리에 참조가 남는데, 초기 구현엔 이전 URL을 해제하는 코드가 없어 대시보드를 다시 조회하거나 QR이 갱신될 때마다 이전 objectURL이 그대로 쌓였습니다.

🛠️
해결 과정

현재 활성 Blob URL을 useRef(qrObjectUrlRef)로 추적하는 clearQrImage() 헬퍼를 만들어, 새 QR 이미지를 받을 때마다 이전 objectURL을 URL.revokeObjectURL()로 먼저 해제한 뒤 새 URL을 저장하도록 바꿨습니다. 컴포넌트 unmount 시에도 별도 useEffect cleanup에서 마지막 objectURL을 해제하고, QR이 비활성이거나 응답이 유효한 Blob이 아닐 때도 clearQrImage()를 호출해 빈 상태로 정리합니다.

✅
결과

페이지 이탈·재조회를 반복해도 Blob URL이 즉시 해제되어 메모리 사용량이 일정하게 유지됩니다. 브라우저 DevTools Memory 탭에서 반복 스냅샷을 떠 확인했을 때 이전에 보이던 계단식 증가 패턴이 사라졌습니다.

관리자 경로 인증 일부 경로 검증 공백 → 전 경로 검증 + 이중화 ✅
⚠️
문제 상황

관리자 페이지는 RoleBasedPageInterceptor가 세션의 ADMIN 역할을 검사하는데, 점검 중 인터셉터가 적용되지 않아 검증 없이 접근 가능한 관리자 경로가 있는 걸 발견했습니다.

🔍
원인 분석

servlet-context.xml의 인터셉터 등록에 <mapping path="/admin/**"/>만 있었습니다. 스프링 AntPathMatcher는 /admin/**를 하위 경로에만 매칭시켜서, trailing 세그먼트가 없는 /admin 루트 자체(관리자 진입점, AdminController가 매핑된 경로)는 매칭 대상에서 빠집니다. 인증을 인터셉터 한 곳에만 의존하다 보니 이 매핑 누락이 그대로 무방비 구간으로 남아 있었습니다.

🛠️
해결 과정

servlet-context.xml에 <mapping path="/admin"/>을 /admin/**와 나란히 추가해 루트 경로까지 커버하도록 정비했습니다. RoleBasedPageInterceptor의 resolveAllowedRoles()가 requestPath.equals(routePrefix) || requestPath.startsWith(routePrefix + "/")로 정확 일치·하위 경로를 모두 검사하는 것도 다시 확인했고, 마스터 계정(userId=1) 보호 같은 핵심 분기는 컨트롤러 레벨에서도 한 번 더 검증하도록 이중화했습니다.

✅
결과

AdminController·AdminBusinessAuthController·AdminBusinessQrController 등 관리자 컨트롤러가 모두 /admin 하위 경로라, 매핑 정비 후 모든 관리자 경로가 인증·역할 검증을 거칩니다. 배운 점: 인터셉터 경로 패턴은 프레임워크의 매칭 규칙(/**는 자기 자신을 포함하지 않는다는 것)까지 알아야 안전하다 — 적용 범위를 명시적으로 관리하고 핵심 로직은 다층 방어해야 한다.

회고 및 배운 점

⚙️

기술적 성장

QR 코드 생성·검증 API를 설계·구현하며 도메인 로직과 인프라 코드를 분리하는 감각을 길렀습니다. Blob URL 메모리 누수 트러블슈팅을 통해 브라우저 리소스 생명 주기와 React useEffect cleanup 패턴을 체득했고, 인터셉터 범위 밖 인증 공백을 직접 발견하면서 보안 관점으로 코드를 바라보는 습관이 생겼습니다.

🤝

협업 경험

5인 팀 리더로 역할 분담과 일정을 조율했습니다. API 파라미터 명 불일치 버그를 직접 겪은 후 팀 컨벤션을 문서화하면서, 프론트·백을 동시에 담당하는 풀스택 포지션에서 인터페이스 계약을 먼저 정의하는 API-first 접근의 가치를 실감했습니다.
